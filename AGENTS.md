# CalorieBank Engineering Rules

## Product Priority

The primary V1 loop is: connect supported data sources -> configure goal mode and the deficit/surplus adjustment when applicable -> automatically sync intake and total-expenditure data -> calculate bank changes -> update immutable ledger -> send one meaningful morning bank update -> explain the balance. V1 also includes Planning Database flows that compare future meal/event estimates against the bank without logging intake.

Do not introduce features outside that loop without explicit approval.

Food logging is secondary in V1. Treat manual entry as fallback, correction, supplementary input, or future expansion, not the dominant product workflow.

V1 includes a Planning Database for future meals and events. Treat Planning Database entries as planning estimates only; they are not confirmed intake, not Food Tracking records, and must not directly change the bank. Connected calorie-tracking applications remain the source of truth for consumed intake. Banking Goals may organize portions of Available Bank under ADR 013, but they are not independent banks and must preserve `goal allocations + Unassigned = Available Bank`.

## Engineering Rules

Beta identity, request ownership, OAuth initiator binding, and environment separation are governed by `docs/product/adr-019-beta-identity-and-environment-boundary.md`.
Opening Bank initialization, non-negative Available Bank presentation, and derived Recovery are governed by `docs/product/adr-020-opening-bank-and-recovery-presentation.md`.
Personalized step contribution and the one-time initial Steps visibility decision are governed by `docs/product/adr-021-personalized-step-contribution-and-initial-visibility.md`.
Historical-first resting-burn estimation and ledger-neutral rest-of-day forecasting are governed by `docs/product/adr-023-resting-burn-intelligence.md`.

- Use TypeScript for new V1 code.
- Use the repository-pinned Node 20 runtime. Expo SDK 54 is not stable under Node 24 in this project.
- Avoid `any` unless a boundary genuinely requires it and the reason is documented.
- Validate API boundaries.
- Banking logic belongs in `packages/domain`.
- Shared API schemas belong in `packages/schemas`.
- Shared compiler and tooling config belongs in `packages/config`.
- Follow `docs/product/bank-calculation-spec.md` for all bank terminology, formulas, initialization, ledger, history, correction, and notification calculation behavior.
- Treat Today as bank-first. Available Bank is read-only, opens Bank History, and must show honest unavailable states until finalized bank inputs exist.
- Preserve the canonical consumer setup journey: authenticate -> connect one expenditure source -> connect one intake source -> configure the goal -> complete the bounded Opening Bank import attempt -> Today. Connected is not ready: each selected role must demonstrate usable authoritative data. A completed import with no matching historical day may enter Today with an uncalculated bank until the first post-signup completed day. Resume from persisted welcome/completion markers and authoritative provider, goal, sync-session, and Opening Bank state; do not create a second setup truth.
- Keep V1 consumer terminology outcome-focused. Normal screens may say connected, refreshing, out of date, may still update, and final; reserve provider resolution, ingestion, OAuth, HealthKit, ledger, and reconciliation terminology for development diagnostics or optional explanations.
- If CalorieBank needs to walk the user through a feature, the feature is too complicated. Make normal consumer interfaces intuitive to a first-time user with no prior context; simplify the presentation itself before adding tutorials, tooltips, modals, or explanatory copy.
- Whenever provider burn and estimated actual burn are presented together, show the `× 0.8` relationship when it is needed for local understanding. Do not repeat the multiplier when that makes the interface cluttered, hard to scan, or unnecessarily redundant within the same screen; prefer the nearest clear explanation.
- Consumer naming should identify the product or device the user recognizes while preserving the provider-neutral transport boundary. Never label a value as Fitbit, Apple Watch, or a nutrition app unless that value's stored provenance or an explicit presentation source supports the claim; fall back to Apple Health or another truthful transport label when writer identity is unavailable.
- Do not equate V1 scope with first-use visibility. Keep the initial experience focused on Available Bank, latest finalized contribution, calculation explanation, and required data status; follow ADR 011 for visibility and ADR 014 for readiness, complementarity, and pacing before exposing optional capabilities by default or adding recommendation behavior.
- Proactive feature recommendations must satisfy Relevance, Familiarity, and Complementarity under ADR 014. Do not use account age, elapsed days, sessions, arbitrary timers, unlocks, or levels as readiness. Manual exploration must remain available where practical.
- Today's Forecast and Projected Daily Burn belong to V1 progressive discovery, but they must remain qualified expenditure estimates. Never turn them into a Projected Bank, deposit, withdrawal, calories-remaining value, or ledger input.
- Time-Aware Activity Forecasting is an advanced layer inside Today's Forecast. Do not implement numeric pace, checkpoint, feasibility, or familiar-activity guidance until ADR 015's forecast method, confidence, freshness, overlap, target, and day-boundary decisions are approved. System data confidence and user familiarity are independent gates; neither implies the other.
- Today's Eating Budget is separate current-day guidance. Do not implement a numeric budget, Remaining Today contract, API, or dashboard card until ADR 012's provider semantics, remaining-expenditure methodology, and signed-goal mapping are approved. It must never modify Available Bank or the ledger.
- Banking Goals are allocation labels within Available Bank, not new balances. Do not implement them until ADR 013's protection, withdrawal-allocation, Emergency Bank order, and correction policies are approved. Goal operations must never create calories or mutate the finalized bank ledger.
- Never stack steps, workouts, active energy, resting energy, personal activity averages, and provider total expenditure when those values overlap.
- Do not implement manual bank-spending, treat-withdrawal, or `Use Bank` actions. Negative completed days reduce the bank through finalized ledger transactions.
- Do not make estimated activity-opportunity calories affect the bank. Activity estimates are planning information only; connected-source expenditure and completed-day finalization remain authoritative.
- Do not use AI or hard-coded copy to invent calorie-burn numbers. Future activity estimates must be deterministic, versioned, qualified as ranges, and based on explicit user preferences or authorized history.
- Do not implement a user-entered absolute daily calorie target for V1. The daily allowance is derived from imported total daily expenditure, CalorieBank's `0.80` V1 adjustment, and the user's signed goal adjustment.
- Integration claims must be technically verified before being documented or implemented.
- Provider ingestion must use provider-neutral interfaces and normalized aggregates. Do not put concrete provider payloads or provider-name switches in domain logic.
- Resolve expenditure, activity context, and intake through the capability-aware provider roles in ADR 016. Never sum steps across providers, merge workout lists across providers, or add workout calories to a provider's total expenditure.
- Follow ADR 017's expenditure qualification classes. Only a verified `FULL_TOTAL` or rigorously documented `DERIVABLE_TOTAL` provider may feed banking. The V1 Health Connections UI exposes Fitbit/Google Health, Apple Health, and FatSecret only. Garmin and WHOOP remain deferred architecture and must not be advertised as supported V1 connections.
- Resolve exactly one authoritative expenditure provider and one authoritative intake provider for every bank calculation. Fitbit-derived expenditure uses Google Health API `total-calories` through the internal `google_health_fitbit` provider identifier. Never sum Google Health/Fitbit and Apple Health expenditure or multiple intake providers. Provider changes may reconcile provisional days with append-only deltas; locked days remain unchanged.
- Treat provider connection and role selection as separate state. Private-beta Calories Burned selection moves expenditure and activity authority together; Calories Eaten remains independent. Never silently change authority when a selected provider disconnects or becomes unavailable: require an explicit role change first, preserve inactive Apple Health writer identity, and keep historical per-day overrides above global selection. Apple Health permission state remains device-owned and must be composed with server role state rather than inferred from historical aggregates alone.
- Keep Health Connections role-first: Calories Burned and Calories Eaten show the selected authority, while compact Burn Sources and Intake Sources inventories show connected role-capable sources. Source rows own direct-provider removal or Apple Health management; secondary details own refresh and troubleshooting. Adding a source is role-scoped, keeps existing services connected, and may select the newly connected source only because the user explicitly initiated that role flow.
- A valid explicit historical source override takes precedence over global provider selection for that user, completed local date, and role only. Historical source changes are provisional-day-only, use persisted exact-date aggregates, remain independent for expenditure and intake, and must be honored by every later reconciliation. Locked days, Opening Bank days, Today, and neighboring dates remain unchanged.
- Follow ADR 018 for direct nutrition providers. FatSecret existing-user diary access requires delegated three-legged OAuth 1.0; OAuth 2.0 client credentials are not sufficient. Persist only normalized daily intake totals, never sum FatSecret and Apple Health, and never turn CalorieBank into a food logger.
- When Apple Health transports calorie intake, exactly one selected Dietary Energy writer bundle is authoritative. Never use or fall back to an all-writer Dietary Energy total. Keep the `apple_health` provider identity while presenting the verified underlying tracker name to consumers.
- HealthKit queries belong on the iOS device. Do not query HealthKit from the API, claim it works in Expo Go, or let current-day HealthKit data mutate the finalized ledger.
- Steps and workout calories are context only. Never add them to active plus basal expenditure, the ledger, Available Bank, or Planned Treat progress.
- Progressive Detail surfaces may explain or forecast activity, but they are ledger-neutral. A2.2 step planning starts from A2.1's projected provider burn at rest and adds only provider calories associated with steps above the current count; its inverse solves the same personal walk/run model for total steps. Neither direction may produce a projected bank value or mutate accounting.
- Consumer composition follows `one concept = one card`: distinct dashboard concepts must render as visibly bounded modules, not loose text sections. Any explanatory calorie contribution must be paired with the current total it contributes toward; this does not apply to signed daily bank contributions.
- Prediction-only features must use defensible pre-signup provider history when available. Do not gate them on CalorieBank account age or post-signup days; return insufficient data only when the connected source genuinely lacks the required historical evidence.
- For prediction-only features, use available pre-signup wearable history and return a useful estimate whenever defensible evidence exists. Insufficient data is a last-resort state, not the default result of conservative thresholds. Derived-model persistence is a cache, not a prerequisite for rendering a forecast. Explain `Why 80%?` through an explicitly identified founder's personal calibration experience in lightweight contextual UI where the multiplier first appears; do not navigate away from Today for that answer.
- Step calorie contribution is an estimate derived from the latest up to five valid same-provider walking/running workouts with paired steps and active calories; one valid workout is sufficient and total expenditure is never divided by steps. Initial Steps visibility separately requires at least three completed authoritative step days averaging at least 10,000 steps, runs once when sufficient data exists, and never overrides an explicit user preference.
- Ledger-style balance records are immutable.
- Preserve one effective accounting truth. Available Bank is `max(0, effective balance)` and Recovery is `max(0, -effective balance)`; never clamp the ledger or create a second recovery account.
- New authenticated users initialize once from at most seven eligible prior completed local days, but only after both selected roles complete a deliberate full-window import attempt. Unqueried dates are not missing dates. Pre-CalorieBank negative net is floored only at this opening boundary, and pre-opening dates must never post again.
- Opening Bank provenance is immutable and separate from active-accounting ledger records, but consumer History presents eligible opening calculation dates in the same chronological day list and detail treatment as later finalized dates. After any authoritative provider sync makes the required completed-day inputs available, invoke the existing finalization orchestration immediately; do not require a later provider refresh to initialize the account.
- Planned Treat progress uses non-negative Available Bank and remains zero during Recovery.
- Completed days post immediately as provisional, reconcile through append-only correction transactions for two local calendar days, and then lock permanently. Never edit an existing ledger transaction or automatically reconcile a locked day.
- Private-beta lifecycle execution is provider-aware: Render runs the account-wide coordinator hourly for authoritative server-readable Fitbit/FatSecret sources, while Apple Health and its exact intake writer catch up only during authenticated foreground execution. Initial posting requires an exact-date authoritative query completed after that local day ended; an earlier current-day cumulative aggregate is not completed-day proof. Lifecycle retries remain bounded, user-isolated, and idempotent.
- Before changing a goal, finish bounded recoverable completed days under the existing goal or reject the change with a recoverable state. Never apply a newly selected goal retroactively to an unresolved completed day.
- Do not store the bank exclusively as one mutable balance.
- Every balance change must be traceable.
- Add tests for calculation changes.
- Never expose secrets to the client.
- Every beta/production `/v1/me/*` request must resolve an internal user from a verified credential. Never trust a client-supplied user ID. Provider callbacks resolve ownership only from expiring, single-use server-side attempts. `DEV_USER_ID` is restricted to explicit local development.
- A local API using `AUTH_MODE=development` must reject Clerk bearer credentials. When `AUTH_MODE=clerk`, every verified Clerk subject resolves only to its own internal user or provisions a fresh one; it must never fall back to `DEV_USER_ID`, email matching, or an arbitrary existing account.
- Do not install dependencies without a concrete reason.
- Run lint, type checks, and tests before completing implementation tasks.
- Keep changes scoped.
- Do not redesign unrelated screens.
- Preserve accessibility.
- Document important architectural decisions.
